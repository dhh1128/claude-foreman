# zamu — design

`SKILL.md` holds judgement for the session doing the work. This holds the decisions and why, for whoever comes next.

## The name

It was called `foreman` for its first day. Daniel asked on 2026-10-12 whether to rename it to avoid the gendered "man", and the builder added a second, independent reason: `foreman` is already a widely used command — Ruby's Procfile process runner, and Red Hat's The Foreman — so a public plugin by that name puts two programs with one name on some users' PATH. Rejected: `steward` (a term of art in Bakobo's own work), `marshal` (Daniel disliked it), `supervisor` (accurate, but beside the supervisord process manager), and `projmgr`/`projsup` (generic and hard to say). Chosen: `zamu`, Swahili for a turn of duty or a watch, in the short coined-or-borrowed family of Bakobo's component names. It tells a stranger nothing, so the plugin description has to. The `foreman` command forwards to `zamu` for one release, and `FOREMAN_*` environment variables are still read, so the two PM sessions running when it was renamed did not have to stop.

## The problem

session-coord keeps sessions in one project from tangling. It has no notion of a plan, and it does not cross repos. The user it was built for runs eight to fifteen Claude sessions at once, and a program of work like a library release rippling through four downstream repos has dependencies that cross repos: a dependency bump that must land in one repo before the next can take it, changes that wait on upstream pull requests only the human may post, decisions that must be recorded before the code they justify.

Before this, the human held that graph. He was the bottleneck and the switchboard: he noticed when an upstream release landed, opened the next window, pasted the next brief, and remembered which repos were waiting on what. zamu holds the graph, launches worker sessions when an item's dependencies are met, watches them, and escalates. It does nothing else.

This was the third time the need came up, which is why it was built generically. One project had already built a bespoke PM as a long prompt (a session told, in prose, to own an agenda file, order five work items, cap workers at four, and tell the human when to launch the next handoff). A second has a hard date — a summit in November — and so needs "what is late", which the first never exercised.

## Decisions, with the reasoning

**The plan and the record are two files.** `plan.toml` is the human's: what the work is and what depends on what. `state.json` is the CLI's: what has happened. Neither writes the other. A person can edit the plan while the PM runs, and the next pulse picks the edit up without either side overwriting the other. The alternative — one file with state fields the CLI rewrites — makes every hand edit a race with the PM.

**Nothing lives in the PM's context.** Every verb reads disk, acts, and writes what it learned before returning. There is no daemon and no in-memory cache, so there is nothing for a crash, a compaction or a reboot to lose. The acceptance test kills a pulse with SIGKILL partway through and checks that a fresh process sees byte-identical state.

**Writes are atomic and locked; unreadable state is refused, never treated as empty.** All three are session-coord's rules, each learned there by losing data. A tolerant reader that returns `{}` for a file it could not parse hands the next write a licence to save `{}` over it.

**An oracle answers True, False or None, and None means could not look.** A `gh` outage read as "not merged" would only delay. Read as merged, it would launch dependents onto a base without the change. So None is never folded into either answer. Same rule as session-coord's liveness, for the same reason.

**A worker's "done" is a claim, checked against the oracle.** A done that the oracle does not confirm holds the item in `review`, flagged. The cost of a wrong done is a dependent launched onto the wrong base, discovered when that dependent's work is half built.

**Liveness is session-coord's, through its command.** That logic took session-coord eleven review rounds: pid recycling, tmux server restarts, panes holding a different claude from the one recorded. A second copy would drift from the first the day either changed. zamu starts each worker with `claude --session-id <uuid>` chosen at launch, so it knows the id before the worker says anything, and a worker is live iff `session-coord board --repo <repo> --json` lists that id. When session-coord cannot be read, the worker is `unknown`, which holds its slot. A dead worker does not. Calling the command rather than importing the package is deliberate: the two plugins are installed and upgraded separately.

**Relaunch resumes the conversation.** `launch --relaunch` uses `claude --resume <the same uuid>` in a new window over the existing worktree, so a worker that died mid-task comes back with its own context. It refuses unless the board says the worker is dead, because a relaunch of a live worker is two workers on one branch.

**Escalation is idempotent by construction.** A decision's ask tag is a hash of the plan name and item id, and the tag is recorded in state once filed. A restart that lost state refiles the same tag, session-coord refuses the duplicate, and zamu records that as already filed. The acceptance test deletes `state.json` after an escalation and checks that the queue still holds one ask.

**`ask add` is checked by its confirmation, not its exit status.** Outside a git repo session-coord prints "not a git repo" and exits 0 having filed nothing. Trusting the exit status would record an escalation that never happened.

**The machine's cap wins.** `max_workers` comes from config (`ZAMU_MAX_WORKERS` overrides it) and defaults to 3. A plan may set its own, which can lower the cap but never raise it: the machine's limit exists because of memory, and a plan written on another machine does not know this one's.

**Launches are data before they are actions.** `launch` builds the exact command list and either prints it or runs it; the dry run is the same list, not a description. The first launches of a plan are dry runs shown to the human, which is a rule in the skill rather than in the code, because after that one review launching is the PM's job.

**Merge contention is shown, not managed.** Two build items ready or in flight in one repo put a line on the board pointing at `session-coord lock merge`. A second lock would have two owners for one invariant.

**Deadlines are a check, not a scheduler.** Items carry `due` (inherited from `[plan] due` when absent) and an optional `estimate`. An item is at risk when the longest chain of unfinished estimates ending at it cannot finish by its due date starting today. That answers "what is late" without pretending to know who works on what, or when. Only a date written on a dependency counts when flagging a dependency due after its dependent; otherwise a plan-wide date inherited by everything flags every item that has an earlier date of its own, which the first version did.

**TOML, so Python 3.11.** Daniel's call, 2026-10-12. The first proposal was INI via `configparser`, to keep session-coord's 3.9 floor for a stock Mac. He chose TOML and 3.11, and `bin/zamu` says so plainly on an older interpreter rather than failing on the import.

**The board is a budget.** A waking PM reads it every time. Attention first, one line per worker in flight, everything merely waiting compressed to ids. A test holds a twenty-item plan's board under 1600 characters, about 400 tokens.

## What the first real plan changed (2026-10-12)

The first PM to run a real plan (five gap items in one repo, one worker already running by hand) reported in its first hour; each item below is its observation, with the cause re-derived here.

**Launched workers were invisible to session-coord.** The PM saw that workers started by `launch` never appeared on `session-coord board`, while a hand-started one did. Cause: `launch` ran claude as the tmux pane's own process, and session-coord looks for a pane's claude only among the pane process's *descendants*, so the record was swept as stale on the next read. Two fixes. `launch` now runs claude as the child of a shell (`sh -c '"$@"; exec $SHELL -l'`), which is the shape of every hand-started window; the trailing `exec` leaves a shell in the worktree when claude exits, as a hand-started window does. And liveness gained a second proof: when session-coord does not list the session, the recorded pane is checked for a process whose argv carries the session id. A worker zamu started always has its id in its argv, so this proves exactly the workers zamu launched, and says nothing about anyone else's.

**Flags did not reach the workers.** Daniel's sessions all run with a permission-mode flag that comes from a shell function, and tmux does not run an interactive shell, so the flag never reached a launched worker, which would have sat at permission prompts in a window nobody watched. The `claude` config key already carried flags; the README now says why it has to. A handoff telling the worker to ask the human before starting was the same failure by another route, so the worker prompt now says the window is unattended and to report `stuck` instead of waiting.

**`adopt` was missing**, because the plan's first worker was started by hand before zamu existed. Added, with a warning when the recorded tree does not exist yet.

**The PM's own report rang the PM.** `attach` records the PM's pane, and a report made from it no longer rings it.

**Merge contention fired from the first launch**, before any PR existed, on every pulse and with no way to acknowledge it. It now fires only when two items in one repo are both in review, which is when merges actually queue.

**Live is not healthy.** foreman1 found, at Daniel's prompting, that workers which read as live had left damage: Codex exited and left three full pytest-xdist suites hung at 0% CPU in one worker's tree for 45 minutes, still holding ports, and a later look found test processes idle for ten days in a worktree deleted at merge. `pulse` now scans the process table for processes in a worker's tree that are orphaned, or in any deleted `.worktrees/` directory, notes whether their CPU has moved since the last pulse, and puts them on the board. Idleness alone is not a finding, because a worker's own claude and shell idle in its tree whenever it waits. `reap` kills only an orphan (reparented to init or the user's systemd) that sits outside every tmux pane, is not a claude, and is in a deleted directory or under a finished item; everything else is the worker's to clean up. The first version also reaped anything in a deleted directory, and foreman1 caught that it would have killed a live interactive Claude session whose working directory was a removed worktree. When tmux cannot be asked which processes are panes, nothing is reapable. Its first dry run on this machine found sixteen processes in two deleted worktrees, none belonging to any plan. The same pulse reads each running worker's tmux window activity, so a worker sitting at a prompt shows as quiet.

## The PM's role, widened (2026-10-12, Daniel's ruling on Q-GCVF)

The founding rule was that the PM does nothing but sequence. Both real PMs broke it in the first day, in the same direction: why-acdc's PM owned status files and verified tests by instruction, and the summit's coordinator spent most of its time turning review rounds into fix orders, running the merge tool and hand-merging under rules Daniel set mid-run. Asked whether to hold the line or widen it, the builder recommended widening it by *kind* of work rather than by permission: the PM does coordination (anything that needs the cross-worker view) and hands execution (anything that blocks or floods context) to workers, including short-lived errand workers. The rule moved from the tool to the session. The `zamu` command still never does work. Daniel agreed completely. Three mechanisms make it concrete: `zamu rules` (standing rules recorded per plan, because a rule held only in context dies at compaction, and the summit's coordinator had kept "rules in force" in a hand-written state file), `owns` (documents the PM maintains, so that work is in scope rather than a deviation), and the skill's rule that a hand-merge needs a standing rule naming the case.

## Workers are not items (R-YJY0)

The first design launched one fresh Claude session per item. The summit's history showed otherwise: two subagents carried four and three items in turn, resumed by message so they kept their context, and an earlier coordinator ran one Claude and three Codex windows that Daniel started himself when his Claude budget ran thin. So a worker is now any agent zamu can address, recorded in a registry, and items are assigned to workers. A worker carrying two items holds one slot. Liveness takes whatever proof the kind allows: session-coord for a Claude session; for a worker zamu launched, a token in the wrapper shell's argv (`zamu-worker:<id>`) that vanishes when the engine exits; for a window someone else started, whether its pane still exists; for a subagent, nothing, so it is `unknown` and the PM reports for it. `assign` records the assignment and prints the brief; the PM delivers it, because how to reach a worker depends on what it is, and zamu guessing would be worse than zamu saying so.

## Finished workers are retired (2026-10-13)

An idle Codex worker held 200–300 MB on Daniel's box, and four finished windows held about 0.9 GB. After those windows were killed, the board still offered them for assignment because pulse checked liveness only while their items were active. The registry now checks idle workers on pulse and before board/list displays, and assignment checks the proof again before recording a new item. An unreadable proof does not revive a worker already known dead; workers with a pane or session are offered as idle only with positive live proof. Subagents have no machine proof and remain explicitly unknown. The alternative was to delete dead registry entries, but retaining their history and a visible dead or retired status explains why they cannot be reused. `worker retire` refuses active workers and dirty linked worktrees, closes a provably owned pane, removes a clean linked worktree, and keeps the branch. The PM is told to retire after completion unless it can name the next item soon.

**Pane ownership is checked again at retirement.** A tmux pane id can be reused after a server restart, so `worker retire` kills a window only when its recorded worker token or session id is still in that pane's process tree. If the pane is gone it can finish retirement without a kill; if the pane exists but ownership cannot be proved it refuses, even for a hand-started Codex window with no token. Rejected: using pane existence alone, which could kill a different worker. If a registered window's liveness cannot be checked, the board shows it as unknown outside the assignable idle list, and assignment refuses to reuse it. Subagents remain assignable with their intrinsically unknown liveness because they have no machine proof to query.

**A successful pane listing proves absence, not ownership.** On tmux 3.6, `display-message -p -t %N '#{pane_pid}'` can exit successfully with empty output for a missing pane. Pane liveness now checks `list-panes -a -F '#{pane_id}'` first: an absent id after a successful listing is dead, while a failed listing, including no server, remains unknown. A present id proves a hand-started worker's pane exists, so liveness may call it live, but ownership remains unproved until its process tree carries the recorded worker token or session id. The world therefore exposes separate pane-existence and pane-ownership questions; retirement never treats an empty identity as ownership. Rejected: treating an empty or failed `display-message` as proof of absence, or a present pane id as proof of ownership, because either can lead to an unsafe retirement decision.

## Done can be undone (R-EPTZ)

In a stack of repos pinned to each other, "done" is a claim about a set of pins. The summit re-ran ten consecutive cold starts for every milestone on each re-pin, and kept SHAs and evidence paths by hand in a narrative plan that drifted. A plan can now declare `[pins.<name>]` with a command that prints the pin's value, and items `rests_on` them. A pin that moves flags every done item resting on it as stale; a pin that moves after its `freeze` date says so. `verify` re-establishes the evidence: by rerunning the oracle, by recording a check run elsewhere (`--ok <evidence>`, for a falsifier too expensive to run in a pulse), or by reopening the item (`--fail`). A reopened item is not closed again by its oracle alone, because the oracle may be the thing that failed to notice. Evidence is recorded with the pin values it was established at. An unreadable pin is never a move.

## Waits on people outside the plan (2026-10-12, the imbu donation)

The third customer's critical path runs through upstream PRs that only the human may post and only a maintainer outside the plan may merge, with lead times of weeks and a fallback strategy whose timing depends on them. Three additions came from it: `waiting_on` and `nag_after` (the board ages each wait and says whose it is, and nags past a budget, because "waiting on the maintainer, 19 days" was the line the case most needed and nothing produced it); `ask_when` on a decision (the fallback is asked only once a named wait exceeds its budget, and never if the wait ends first); and an `A`-kind ask filed automatically for an external item waiting on the user, so "go and post this" reaches them with the draft's path rather than depending on a worker remembering to file it. zamu still never posts anything. It notices, read-only, that the user has.

## The watcher, and the reversal of "no daemon" (2026-10-12, Q-EZMY)

The first design had no daemon: every command read disk and returned, and the PM session drove everything. That left launching waiting on a model to wake up. A slot freed by a merge or a dead worker sat empty until a worker report or a fallback timer happened to wake the PM. Daniel: "A foreman that I have to prod to do something isn't very helpful." The fix splits the work by kind. Launching, once the user has approved a plan's dry run, is mechanical, so a process does it: `zamu watch` pulses every plan, launches into free slots on plans marked `autolaunch`, and messages the PM through session-coord only about what is new (launches, state changes, new attention lines, keyed with their numbers blanked so an ageing wait is one key). Waiting in a process costs nothing; waiting in a model turn costs tokens. The original objection, that a daemon must be kept alive across reboots, is exactly what a systemd user service provides, so the decision is reversed rather than worked around. Without systemd, a PM runs the same command as a background task with `--exit-on-news` and is woken by its exit. The watcher re-reads config each tick, so a changed cap takes effect without a restart, and it finds session-coord through the plugin install record, because nothing in a Claude session's PATH reaches a systemd service.

## Replaceable PMs (2026-10-13)

Each plan has a `pm.md` standing brief, created by `init` and maintained with its plan. `pm start` and `pm restart` open a fresh Claude session, point it at that brief, and tell it to attach and pulse. Resuming the old conversation was rejected because a dead or exhausted context is the failure being recovered from. The session-coord board for the attached repo and target is the liveness authority; an unreadable board is unknown, never dead. If the PM is confirmed gone while workers or attention remain, the watcher files one `A` recovery ask. It files a new ask only after seeing the PM alive between outages. Automatic restart was rejected for now because choosing to spend another PM session stays Daniel's call. The CLI dry run prints the exact tmux command before `--go` executes it.

**PM names are visible and reserved (2026-10-14).** PM starts and restarts use `<plan>-prj` for the tmux window, Claude's `-n` display name, and the session-coord attachment target, while retaining a UUID for `--session-id` and process ownership. Plan validation rejects any item topic ending in `-prj`, including a default topic inherited from its id, because worker windows use topics and the suffix must identify a PM in window lists. Rejected: the old `zamu-<plan>` window and UUID target, which made the PM harder to find by name; also rejected: changing the UUID session id, which is still the stable identity used to track the launched process.

**Seeing the PM alive updates state without waking it.** The first lifecycle watcher treated `PM seen alive` as general watcher news and messaged the same PM, spending a turn to tell it only that it existed. The watcher now filters that one change from PM notifications while keeping the live state for outage recovery. Rejected: suppressing the liveness check itself, because the recovery ask must be rearmed only after a confirmed live interval.

## Admission is measured, and the box's (2026-10-12, Q-TFQ2)

The cap began as 4, which was Daniel's per-session subagent limit carried over, and it could not see anything else on the machine: on the day it was measured, 21 claude processes used 6.5 GB, while the real load came from test suites that take every core. A fixed count of workers is the wrong unit. `admission` names a command asked before each launch: exit 0 admits, 75 means not now (the board says why), and anything else means it could not look, in which case the count cap alone applies and the board says so. On Daniel's machine that command is devenv's `headroom`, which reads Linux pressure-stall times and available memory; it lives outside zamu because the policy is the box's, not the plan's. With admission on, the watcher launches at most one item per tick, because a new worker does not load the box until it gets going, and filling every slot against one idle reading would admit them all at once. `max_workers` stays as a backstop.

## Engine budgets (2026-10-13, Q-KBKV)

On 2026-10-13 Daniel had used 76% of his Claude weekly limit with about 40 hours to the reset, and every zamu worker was a Claude session, so that is where the spend went. zamu had `engine` per item, `[engines]` commands and `[engine_caps]` counts, and measured nothing. Daniel ruled that budgets are measured admission, like `admission` and devenv's `headroom`: a tool measures, a launch picks an engine the budget admits, and the human decides only trade-offs, such as buying more Codex or slowing a plan. A count cap on an engine is not a budget. It limits how many sessions spend at once, not how much is left to spend, and it cannot tell a Monday from the last day before a reset.

**The probe is a command per engine, with admission's contract.** Config names it:

```toml
[budgets.codex]
probe = ["budget", "codex", "--max-pct", "60"]

[budgets.claude]
probe = ["budget", "claude", "--projects", "~/.claude/projects", "--max-pct", "85"]
```

The command exits 0 to admit, 75 for not now, and anything else (or a 30-second timeout, or failing to start) for could not look. Its stdout is one JSON object: `{"used_pct": 71.0, "resets_at": "2026-10-15T17:00:00Z", "estimate": true, "figure": "~71% of allowance, resets Thu 17:00"}`. Every field is optional; `figure` is what the board shows, and `used_pct` and `resets_at` are what the trade-off ask quotes. The verdict is the exit code, never a number zamu compares, so the threshold is the user's and lives in the probe's arguments. An engine with no `[budgets.<name>]` entry has no budget and is always admitted by this check; caps and box admission still apply. Two engines whose probes are the same argv are probed once per tick, which is how two Codex command variants share one account.

The alternative was probes built into zamu. A command won on three counts. The Codex quota rules already exist in devenv's `prmerge/hostile.py` (`_last_rate_limits` and `read_quota`) and were corrected twice by reviews of dhh1128/devenv#28: a newest-file cutoff that hid an older 70% reading, and a reached limit ignored when the rollout carried no window data. A copy inside zamu would miss the next correction, while a command can import `read_quota` and stay one implementation. Second, engines are arbitrary names in config, and built-ins would cover three of them. Third, the threshold is the account owner's policy, as the box's pressure limits are, and `admission` already puts that kind of policy outside the plan. The cost is that a stranger installing the plugin gets no probes. The contract is documented in the README so one can write one.

**The probes live in devenv as one `budget` command, beside `headroom`.** Each subcommand prints the JSON above and exits with the verdict.

- `budget codex [--sessions ~/.codex/sessions] [--max-pct 60]` calls `prmerge.hostile.read_quota(sessions_dir, now=..., threshold=max_pct)` and maps its result: `blocked=True` is 75, `readable=False` is 2 (could not look; zamu does not then fall open the way hostile does, see below), otherwise 0. `used_pct` is the highest live window, `resets_at` that window's. On this box the rollout reports one window, `primary`, of 10080 minutes (weekly), on plan `prolite`. The 60% default is Daniel's existing threshold for automation, from `hostile.py`, and is not re-derived here. One change is needed in `hostile.py`: `Quota` must also carry the highest live percentage and its reset epoch, which today exist only inside `note`. Adding two fields to the dataclass is that change.
- `budget openrouter [--min-usd 5]` reads the key with `llm keys get openrouter` and calls `GET https://openrouter.ai/api/v1/key`. When the key has a `limit`, `limit_remaining` is the figure; otherwise `GET /api/v1/credits` and `total_credits - total_usage`. Not now below `--min-usd`. Both endpoints answered on this box on 2026-10-13. A key failure or HTTP error is could not look.
- `budget claude --projects <dir> [--max-pct N] [--allowance W] [--reset <weekday HH:MM tz>]` is an estimate, and says so: `"estimate": true` and a leading `~` in the figure. No machine-readable weekly-limit percentage was found on this box. The probe sums per-message `usage` from every `*.jsonl` under `<dir>`, recursively, because subagent transcripts sit in `<session>/subagents/`. It reads only files modified since the window began, counts records by their own `timestamp`, and counts each `message.id` once: a message's `usage` is repeated on every line of its streamed content (one transcript on 2026-10-13 had 10 usage lines for 7 messages). Tokens are weighted by API list-price ratios, `input + 1.25*cache_write_5m + 2*cache_write_1h + 0.1*cache_read + 5*output`, times a per-model factor from the probe's config (relative list input price, Opus 5 : Sonnet 3 : Haiku 1 by default). Whether Anthropic's subscription meter weighs tokens this way is not known. The window is the seven days before now, or, with `--reset`, the current week anchored on that weekday and time, which matches how the real limit resets. `used_pct` is the weighted total over the allowance `W`. `budget claude calibrate <pct>` sets `W` from a reading Daniel takes off the Claude usage page ("76% now" makes `W = current_total / 0.76`) and stores it in `~/.config/budget/claude.toml`. Calibration fixes the scale; it does not fix a wrong weighting when the mix of models or caching changes. The probe takes one `--projects` directory, so each Claude account (`~/.claude`, `~/.claude-provenant`) is its own budget and an engine is tied to one account by its command.

**An item names an ordered list of engines it may run on.** `engine = ["codex", "claude"]` means codex if admitted, else claude. A string is a list of one, so every existing plan still parses and means what it did. The alternative was a class, `work = "implementation" | "judgement"`, which config maps to engine orders. A class only pays off when many items move between engines at once, and plans are small. It also hides from the reader of a plan what an item will actually run on, and that is the question a budget shortage makes urgent. The PM edits `plan.toml`, so changing the list is cheap. An item that needs Claude's judgement says `engine = "claude"` and waits for Claude.

**How launch chooses.** For each ready item, `ready_to_fill` and `prepare` walk its list in order. They skip an engine at its `[engine_caps]` count or missing from `[engines]`. Of the rest, the first whose budget admits wins. If none admits but one could not be looked at, the first unknown one wins and the board says the budget was unknown. An engine whose budget says not now is never chosen. This differs on purpose from hostile.py, which falls open to codex when no rollout is readable: there a failed call costs one review, here it costs a worker's whole session. Unknown still beats waiting forever, because a probe that breaks must not stall every plan, and the board line makes the breakage visible. The chosen engine is recorded on the item (`rec["engine"]`, which `commit_launch` already writes), and every place that reads `it.engine` (`engine_load`, `admission_can_block`, `prepare`, the `Launch`) reads the recorded engine for a live item and the list for a ready one. `admission_can_block` becomes "some ready item has an engine under its cap". Budget probes run after box admission says yes, at most once per engine per tick, in the same one-launch-per-tick rule, because spend, like load, does not show until the worker gets going.

A relaunch keeps the recorded engine and is not budget-gated. Only Claude resumes a conversation, the work so far is in that engine, and a relaunch is already an explicit PM act that skips box admission today. A live worker is never moved to another engine: zamu decides only at launch.

**Readings are the account's, so they are stored once for the machine.** The watcher refreshes every configured budget at most every `budget_refresh_minutes` (default 10) and writes `budgets.json` at the state root under `store.locked(config.home())`: per engine, verdict, the JSON, and when it was read. A launch re-probes only the engines it is choosing between, under the machine lock it already takes in `commit_launch`. A reading that could not be taken is stored as unknown with the reason, never as zero and never as the previous reading.

**What the board shows.** One line per configured budget, whatever the plan: `budgets: codex 3% of week, resets Oct 20 · claude ~71% (est.), resets Thu 17:00 — not now`. An unknown budget is an attention line, as unknown admission is. An item waiting because none of its engines is admitted says so in its own row: `ready, waits for budget (codex, claude)`.

**What reaches the human is one ask, and only for a trade-off.** A trade-off exists when a ready item has waited `budget_ask_minutes` (default 60) because every engine in its list says not now, so the plan has stalled for money rather than for load. The watcher then files one ask per plan through the usual escalation (or lists it on the board under `escalate = "none"`). The ask names the waiting items and their engine lists, each engine's figure and reset time, and the choices: wait until the earliest reset; add an engine to the items' lists; raise a probe's threshold; buy capacity, such as a larger Codex plan or OpenRouter credits. It is one episode, keyed like busy admission: it is not repeated until some waiting item's engine has admitted again or the earliest reset time has passed. Nothing else about budgets reaches the human. There is no warning as a figure climbs, no forecast of when it will run out, and no message when a budget recovers; the board carries those for anyone who looks. Rejected: an ask whenever a budget crosses a threshold, because a crossing changes nothing while another engine still admits, and that running commentary is what Daniel asked not to get.

**Out of scope.** Buying capacity or changing a plan tier, which is the human's. Splitting one account's budget between plans; the reading is the account's, and two plans draw on it first come first served. Estimating what an item will cost before it runs. Moving a live worker between engines. Claude's shorter session window (the five-hour limit), which the transcript sum could estimate the same way but which did not cause this; a probe can add it later without a contract change. Spend by sessions zamu did not launch is not separated out, and should not be: it uses the same allowance. Engine caps stay as they are, a count for a reason other than budget (Daniel's note of 2026-10-13: the cap of two live Claude workers set that week was a temporary measure and is not a default, so nothing ships with a Claude cap or presents one as typical).

**Implementation decision (2026-10-14).** The budget probes ship in `zamu budget` and `bin/budget`, using a port of hostile.py's Codex quota guard, rather than living in devenv as first designed. The engine-budgets worker brief explicitly required porting that guard, and a plugin install cannot assume the user's machine has devenv. The probe command contract remains separate from launch policy, so an account owner can still replace any shipped probe. CPU and memory unknown readings fall back to the worker count because that count bounds concurrent load; a budget's unknown reading loses to a known admitting engine because a new worker can spend a substantial share of the account's allowance. When no engine admits, an unknown reading wins to avoid stopping a plan indefinitely on a broken probe. An item's budget wait age survives busy-box, full-slot, and engine-cap ticks while the item remains ready; resetting age on each load interruption could prevent the trade-off ask for an entire exhausted week, as review round 1 showed. Its timer ends when the item leaves ready state.

## Item tiers and models (2026-10-14)

**An item names the judgement tier; the box chooses the model.** A build item can name `tier = "deep" | "standard" | "light"`; the box's `[models.<engine>]` maps that tier to a model id, with optional Codex `reasoning_effort`. The alternative was distinct engine names such as `claude-sonnet`, but those split one account's budget, evade the Claude-only guard, and break Claude-only resume. The item can set an exact `model` for an exception; it takes precedence over the tier mapping. No tier or model leaves the engine default untouched, preserving old plans. A tier with no mapping for the chosen engine refuses launch instead of silently spending a different model. The chosen model, tier, and reasoning effort are stored with the launch so a later config edit does not rewrite what ran. A relaunch with no recorded model fields also keeps the original engine default, because a tier added since launch must not change a resumed worker's model. `zamu show` uses recorded model fields only for the current active worker; a finished or dead worker's record does not override the plan's current tier mapping. An unreadable box config produces a coded error; assuming engine defaults was rejected because it would misstate the planned spend. `claude --help` on this box lists `--model <model>` with aliases including `fable`, `opus`, and `sonnet`; `codex --help` lists `-m, --model <MODEL>` and `-c, --config <key=value>`, which supports `model_reasoning_effort` as a config override. The dry run shows the resolved choice before approval. Live engine launches with these flags have not been probed; the suite exercises generated argv with fake tmux.

**An explicitly selected box config must be readable.** A missing default config remains optional, preserving first-run behavior. A missing path selected with `ZAMU_CONFIG` or `FOREMAN_CONFIG`, or one that cannot be decoded, produces a coded error. The alternative was to treat every missing file as an empty config, but a mistyped explicit path could silently launch on default worker limits and models. This distinction was made after the fix-diff hostile review reproduced both failures.

**Parked sessions keep their launched model when resumed.** Park-idle added a second resume path after the model work began. It uses the same recorded tier, model and reasoning effort as a dead worker's relaunch, including the engine default for an old record without model fields. Recomputing from the current plan was rejected because it could change the model in the middle of one conversation.

**A missing tier mapping blocks only that item.** The watcher skips an item whose selected engine has no model for its tier, leaves the worker slot available for another item, and puts the configuration error in board attention. An item or box model or reasoning effort containing a NUL byte is rejected when the plan or config loads, before worktree setup. While a worker is parked, `zamu show` displays the recorded launch model because its next resume continues that conversation; after the launch ends, it displays the current planned choice.

## Quiet watcher episodes and process ownership (2026-10-13)

**A busy box is one admission episode per plan.** The first watcher keyed attention by rendered text with digits removed. That still changed when pressure moved between CPU and memory, or when a clear reading briefly removed the line; it rang PMs even when no slot was free. The watcher now stores when it last sent the busy line, repeats it only after admission has returned yes or an hour has passed, and asks admission only when a ready item fits the machine and engine caps. A completed launch also rearms the episode: admission can say no in pulse and yes when launch preparation checks again, so pulse's stored reading alone misses a successful admission. A late busy result during launch preparation is a retry for the watcher, not an error to send the PM. Rejected: treating every cleared line as a new episode, because brief clearings do not change the PM's decision or the box's capacity.

**A leftover must have aged and stayed idle across observations.** A reparented process alone is not evidence of damage: Claude Code intentionally reparents its `run_in_background` snapshot shells to pid 1. The scan excludes those shells and requires both process age and unchanged CPU for the configured idle interval before reporting or reaping any process. Rejected: reporting a process on the first orphan observation, because it woke a PM about shells only seconds old. This delays finding a real leftover until a later scan, which is deliberate.

**Explicit worker identities outrank worktree paths.** A `zamu-worker:<id>` token or `--session-id <id>` ties a process to the plan and item that launched it, even after its working directory is deleted. A live worker in that state is reported immediately only to its own PM as a live worker in a deleted worktree and is never reaped; it does not have to pass the leftover age and idle gates. Rejected: labelling every process in a deleted path as an unowned leftover, because a live worker from another plan can be there. Worktree path remains the fallback when no explicit identity is present.

**A child inherits the closest known worker identity in its process ancestry.** MCP servers and other helpers often have no worker token or session id in their own command, but their live Claude parent does. The process scan now follows parent ids within the same snapshot before falling back to the child's worktree path. A child of a live worker in a deleted worktree is reported to that worker's plan as part of the live worker and cannot be reaped, even if its own directory would otherwise look like another plan's leftover. Rejected: assigning each process only by its own command or cwd; that reported a live worker's `confer-server` to unrelated PMs. If an ancestor was inaccessible or exited before the scan, the existing worktree and pane protections still apply.

## What was harvested from the bespoke PM

The bespoke PM was a prompt kept in a private repository. zamu took from it: a brief shared by every worker (`common_brief`), a free-text `ref` field for the item's tracker id, a worker cap, and the conductor-and-ask discipline. It differs on one point that mattered: the prompt PM told the human to launch the next worker when its dependency merged. Launching is the thing zamu exists to take off him.

It also modelled a decision *inside* a work item ("G14 stops once for approval of a decision node"). zamu models decisions as items of their own, so the dependency is visible on the board. A worker that hits an unplanned decision reports `stuck`, and the PM files the ask.

## Declined by its second customer

The summit build, with a hard date five weeks out, was offered zamu on 2026-10-12 and its conductor declined, for reasons worth keeping. What remained was a few sequential items gated on the human's decisions. Its state already lived in a narrative plan, ticks and the session-coord ask queue, so a plan file would have been a second copy. And it dispatched work as resumable Agent subagents, not tmux sessions, so zamu's launcher would have been a second dispatch mechanism. zamu's value is concentrated where items run in parallel and outlast one session. A plan that is mostly sequential, gated on decisions, and run by subagents gets little from it, and switching mid-stream costs more than it saves. zamu cannot launch or watch a subagent at all. That is a gap if subagent dispatch turns out to be common.

## Rejected

- **INI** (configparser, Python 3.9). Proposed; Daniel chose TOML.
- **A daemon or an MCP server.** It would need a process kept alive across reboots, which is the very failure the disk-only state exists to survive.
- **The Workflow tool.** Workflows run subagents, not sessions, and need separate opt-in.
- **Reading worker transcripts to judge progress.** Expensive on every wake and unnecessary: workers report one line, oracles say what is done, session-coord says who is alive.
- **Trusting a worker's "done".** See above.
- **Its own merge lock, its own liveness, its own message channel.** session-coord has all three.

**Worktree report files.** A confined worker can append `<ISO time> <state> <line>` to `.zamu/reports`; pulse reads complete newline terminated records for active items only. It stores each file's byte offset in the same atomic `state.json` write as the report effects, so a crash before that write replays the whole line and a crash after it skips the line. The alternative was to move or truncate consumed lines, but that makes a crash between moving the file and updating state lose reports, and requires a sandboxed worker to cooperate with state outside its worktree. The normal command and file path use the same report state transition. Malformed lines advance the offset but remain visible as attention entries with the path and byte position. An absent file is empty; an unreadable file raises attention until it can be read again. The launcher creates `.zamu/.gitignore` containing `*` before starting the worker.

**A saved offset also needs a prefix fingerprint.** A worktree can be recreated at the same path, and a worker can rewrite its report file in place. A path keyed offset alone would skip early lines in a new file once it grew past the old offset. Pulse now stores the device and inode plus a SHA-256 hash of the consumed byte prefix, and rereads from byte zero if the prefix differs or the file has shrunk. If the prefix is identical, it keeps the offset even when the inode changes, so a copied file does not replay old lines. This was chosen over inode alone because an in-place rewrite keeps the inode. A replacement containing both old and new lines with a changed prefix may replay old lines; without per-line IDs, preserving those new lines takes priority over silently skipping them. Transient read errors are a separate attention field cleared by the next successful read; malformed-line records remain visible.

**Read failures are attention only while a worker is active.** An item can finish through a command, oracle or PM action before its report file becomes readable again. The board suppresses `report_read_error` outside `running` and `review`, because those items no longer need file ingestion. This was chosen over clearing the field in every completion path; the saved error still explains what happened if the item is inspected later.

## Prompt-line provenance (2026-10-13)

In a temporary real Claude Code tmux pane, `tmux capture-pane -e -p` showed an automatic suggestion after the input `❯` as `\x1b[2mTry "how does <filepath> work?"\x1b[0m` (dim). Text entered into that same prompt with `tmux send-keys` appeared as plain `zamu sgr probe typed`, with no style SGR code. Existing panes also showed dim suggestions. Therefore the PM skill requires `-e`, calls dim text a suggestion, and calls plain text only "typed at the prompt" without assigning its author. Daniel's authorship requires his confirmation. Rejected: treating all text after `❯` as his input, because suggestions use the same prompt line; also rejected: requiring bold to recognize typed text, because the real typed probe was plain. zamu code reads pane activity timestamps and process identity, not pane content, so the rule currently has no code path to apply to.

## Portfolio accounting (2026-10-14)

The portfolio reads each plan's state and definition independently, reports a broken plan rather than stopping the board, and still counts slots held by its readable state. Process ownership follows the closest known worker token or session id in a process's ancestry before using its worktree. RSS comes from the process table and CPU% from a short two-snapshot sample. Claude spend uses the same model and cache weights as the budget probe; a Codex worker's rollout is selected by its worktree and creation time because zamu's wrapper token is not Codex's rollout id. Spend is shown by engine because Claude's weighted tokens and Codex's raw tokens are different units. Rejected: interpreting an unreadable transcript or process table as zero, because that would make a busy plan look idle; also rejected adding weighted and raw tokens into a single plan total, which would have no clear meaning.

Review clarified three related cases. A PM's saved status is historical, so the portfolio says `?` unless session-coord answers during this read. A dead PM's recovery ask carries the number of unfinished plan items, since restoring that PM affects the whole unfinished plan. If one worker transcript is unreadable, the board keeps measured spend from its peers and appends `+?`; it does not erase known usage. Worker resource keys include both plan and worker id, and a repeated token across plans is resolved by the closest worktree in the process ancestry. Rejected: using a bare worker id as an identity, because unrelated plans commonly reuse item ids.

**Parking keeps a conversation and dirty worktree while returning the slot (2026-10-14).** Claude workers launch with a chosen `--session-id` and resume with `--resume <id>`; this box's `codex resume --help` confirms `codex resume <id> [prompt]`, and Codex rollout metadata carries its generated session id and cwd. zamu only parks when it can identify one resume session, prove its own pane still runs that worker, read the pane's process tree and activity, see no extra child and no CPU change across the configured interval, verify the merge lock is free, and list dirty paths before closing the window. A reported wait and a quiet pane both require that idle proof. Rejected: parking on a report or pane timestamp alone, because a merge waiting on CI may have no CPU while its child process is still doing work. The saved ask IDs can drive watcher resume only when they were observed open at park time and a readable ask queue later shows them all absent; this prevents an unfiled ask in a report from causing an immediate restart. An unlabelled wait needs a PM's `--unblocked` reason. Resume goes through the launch slot, admission and engine budget checks.

## Box priority and slot reserves (2026-10-14)

Priority and reserve live in the box config, rather than in a plan file, because one plan must not be able to raise itself above its neighbours or claim the box's finite slots. The all-plan watcher pulses every plan before allocating slots, serves plans below their reserves first, then ranks ready items by priority and ready age. The alternative was the old per-plan fill loop, where iteration order let the first plan consume all slots. A reserve is a floor to fill when ready work exists, not a claim that evicts a current worker: priority and reserves never preempt. Every launch still passes admission, engine caps, budgets, and the locked machine cap check. `zamu priority` edits the config under a lock and logs the actor and change in `priority.jsonl`. A single-plan watcher still fills only its selected plan; box-wide priority requires the all-plan service.

## Known gaps — what has not been verified

**Feedback and friction accounting (2026-10-14).** Feedback is an append-only JSONL file under the state root. The first feedback write, list, or portfolio read imports dated bullets from the old field notes under the same state-root lock; a content-derived source id keeps repeated imports from duplicating notes. Rejected: a one-shot marker, because notes added to the old file after the first import would disappear. The portfolio reads each plan's events for weekly counters; adoption, report pane, wait nag, and launch hold transitions add events where the old log had no evidence. Hold start/end transitions use a small state cursor to avoid one event per watcher tick, while durations are computed from the event log and split across week boundaries. Rejected: incrementing counters in state, because it would make a second source of truth and could drift after a crash. A wait crosses `nag_after` once per ready episode, and the event records the observed crossing time; it is not backdated to a tick that did not run.

**Review refinement.** Admission and budget are independent reasons an item may wait, so one ready item can open both holds. The budget trade-off policy still excludes items currently blocked by admission; only friction accounting ignores that gate. A missing hold-end event closes at the item's next state-advancing event, such as assign, launch, report or oracle completion, so a crash between launch and the next pulse does not add phantom wait hours. Rejected: carrying every unmatched start to the portfolio read time. A report event saves `from_pm` while the plan transaction holds the PM pane; comparing an old report with today's PM pane would lose reports after PM replacement and attribute old worker reports to a new PM using that pane.

**Friction accounting gaps.** A direct launch command refused by admission or budget is counted only if a pulse observes the held ready item; there is no event for a refusal that begins and ends between pulses. Existing historical events have no report pane or adoption marker, so those past occurrences cannot be reconstructed. The 70 existing field-note bullets were migrated on this machine and an immediate second import added none; a full week's counter trend has not been verified outside fixtures.

**Priority verification gap.** The cross-plan scheduler has fake-world and git-worktree tests, but a live multi-plan systemd watcher with priority changes during a tick has not been exercised.

If a Codex worker starts another Codex session in the same worktree before its own rollout is written, the portfolio's worktree and creation-time heuristic can choose the wrong rollout; a direct rollout id in zamu's worker state would remove that ambiguity. The live portfolio command has not been verified against another user's process permissions or a non-systemd host.
**Parking has been tested with fake process, tmux, git, and session-coord responses only.** A real Codex rollout lookup and a real window close/resume have not been exercised end to end. The read-only Codex lookup requires exactly one matching session created after launch; otherwise zamu leaves that worker live.

**Model flags have been checked in `claude --help` and `codex --help`, but a real model-selected worker launch has not been run.** The acceptance suite checks generated commands and launch records with fake tmux and engines; it does not prove that a live engine accepts the chosen model id or Codex reasoning setting on this box.

**Engine budget probes have been tested against fixtures only.** The Claude estimate's weighting has not been compared with Anthropic's own meter across a week, so how far one calibration holds is unknown; how long the transcript scan takes on a busy week (406 transcripts were modified in the seven days to 2026-10-13, in 2.9 GB under `~/.claude/projects`) has not been measured against the 30-second probe timeout; and whether OpenRouter's `/key` and `/credits` need a non-management key on another account has not been tried. A real Codex launch with the per-project trust override has not been tried.

**Other input styling remains unverified.** The probe covered a dim suggestion and plain typed text in one Claude Code build and theme. Other styles or a capture without rendering codes are left unattributed.

**Worker retirement has only been tested with real temporary git worktrees and fake tmux.** Closing a real worker window and removing its worktree have not been tried end to end on a running plan.

**The pane listing fix has only been tested with fake tmux.** Its empty successful `display-message` response reproduces the observed tmux 3.6 behavior; a real server and pane disappearance between listing and process lookup have not been exercised.

**Known gap for file report audit:** `events.jsonl` is appended while `state.json` is still in its transaction, as with command reports. A process crash after the event append but before the atomic state write can leave a duplicate event when the file line is replayed. The report state, offset, and PM message remain safe; the event log's existing write order is not a cross-file transaction.

Reported by the first real PM and not yet built:

- **Not yet built, from the summit's history:** named fallbacks with a cut order; decisions with a default-until-answered, a decide-by date and ordering; ranking the user's queue by what each answer unblocks; announcing one outside blocker to every item it holds; copying ignored evidence out of a worktree before it is removed. The analysis is kept privately, outside this repository.
- **Decision gates inside a build item** are now reported as `waiting`, which puts an attention line on the board (the PM had seen gated workers report `running "...awaiting Daniel"`, which the board did not flag). The ask itself is still filed by the worker, not by zamu.
- **The PM is not registered where its workers are.** Claiming the conductor role in the work repo needed a hand `session-coord register` there. `attach` could do it.
- **`zamu` is not on PATH in a session that predates the plugin install**, and the versioned cache path changes on every update. A stable shim outside the plugin would fix it; none is installed by the plugin.

- **A real launch has never run.** The acceptance tests drive real git (worktrees created from a bare origin) but fake tmux, claude, gh and session-coord. Untested: that `tmux new-window … claude --session-id <uuid> "<prompt>"` starts a worker or PM that takes the prompt as its first turn; that session-coord's SessionStart hook records the same id that was passed to `--session-id`; and that tmux-claude's `save`/`restore` round-trips a worker started this way.
- **PM replacement has only been exercised with fake tmux and session-coord.** The real board was inspected for its `title`, `pane`, and `session_id` fields, but an actual PM death, recovery ask, and fresh restart have not yet been tried end to end.
- **The PM's ask repo.** Asks go to the project recorded by `zamu attach`, else the directory `pulse` runs in. If that is not a git repo, session-coord files nothing, and the board says the escalation failed. Not tried against a real queue.
- **Closing a decision is manual** (`zamu mark <id> done`). The PM has to notice the answer; pulse does not read the ask queue, because session-coord has no machine-readable `ask list`.
- **No `hold` or `defer`.** A decision the human has deliberately deferred is still escalated once. The plan can only express it by leaving the item out, or by marking it abandoned.
- **An oracle that holds closes its item even while the item's dependencies are open.** That is right for an external event that happened early, and surprising for a build item: a `cmd:` oracle that happens to exit 0 closes the item without a worker. Write build oracles that can only hold once the work is merged.
- **Stall is measured from the last report**, not from activity in the worktree. A worker that works for five hours without reporting is flagged.
- **Deadline arithmetic is calendar days**, with no notion of working days or of parallel hands.
- **Python 3.11 is assumed, not tested on other versions.** The suite runs on 3.11.
- **Process ownership needs a registered worker identity.** A deleted-worktree process without a matching token or session id in its readable ancestry in a known plan still falls back to path-based "no item" reporting; processes in this class cannot be attributed safely. The Linux `/proc` scan and the watcher service have not been exercised as a real multi-plan systemd run after the quiet-watcher and ancestry changes; the suite uses process snapshots and fake session-coord.
